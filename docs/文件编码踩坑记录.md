# 文件编码踩坑记录

## 个人感受
这个问题让人自己来一个个改更快！！！


## 需求
在 Windows PowerShell 环境下批量替换 Python 文件中的导入路径（`from core.workspace import` → `from core.path_policy.workspace import`），修复团队文件页面的导入错误。

## 错误历程

### 错误 1：PowerShell `Set-Content` 默认编码损坏 UTF-8 文件

**现象**：执行替换命令后，Python 启动时报错 `SyntaxError: invalid character '�' (U+FFFD)`，代码中的中文字符全部变成 `�`。

**根因**：PowerShell 5 的 `Get-Content` 和 `Set-Content` 默认使用**系统编码**（Windows 中文系统为 GBK/GB2312），而项目文件是 **UTF-8 编码** 的。

执行的命令：
```powershell
(Get-Content "core\routes\routes_api.py") -replace 'from core\.workspace import', 'from core.path_policy.workspace import' | Set-Content "core\routes\routes_api.py"
```

UTF-8 中的中文字符通常占用 3 个字节，例如：
- `错` = `E9 94 99`（UTF-8）
- `误` = `E8 AF AF`（UTF-8）
- `：` = `EF BC 9A`（UTF-8）

当用 GBK 编码读取这些 UTF-8 字节时，会错误解释成其他字符。再用 GBK 写回去时，字节序列已经被破坏。Python 用 UTF-8 解码已损坏的字节时，遇到无法识别的字节就用 `�`（U+FFFD，Unicode 替换字符）代替。

**教训**：在 Windows 上操作包含非 ASCII 字符（中文、日文等）的文件时，必须显式指定 UTF-8 编码。

**修复**：
```powershell
# ✅ 正确：指定 UTF-8 编码
(Get-Content "core\routes\routes_api.py" -Encoding UTF8) -replace 'from core\.workspace import', 'from core.path_policy.workspace import' | Set-Content "core\routes\routes_api.py" -Encoding UTF8
```

---

### 错误 2：双重编码损坏无法自动恢复

**现象**：尝试用 Python 脚本自动修复（`raw.decode('gbk').encode('utf-8')`），失败。

**根因**：UTF-8 → GBK → UTF-8 的双重编码过程是**不可逆的**。当 UTF-8 字节被 GBK 错误解码后，部分字节组合会变成 GBK 的有效字符，再次编码时信息已经丢失。

```python
# ❌ 无法恢复：信息已丢失
raw = b'E9 94 99 E8 AF AF'  # UTF-8 的 "错误"
fixed = raw.decode('gbk').encode('utf-8')  # 结果不是原始的 "错误"
```

**教训**：编码损坏后，最好的修复方式是从备份恢复。如果没有备份，只能手动修复或重新编写损坏的部分。

---

### 错误 3：未检查文件编码就批量操作

**现象**：一次性替换了所有 `from core.workspace import`，导致多个文件同时损坏。

**根因**：没有先检查文件的实际编码格式，也没有测试单个文件的替换效果，就直接全局替换。

**教训**：批量操作前，先在一个小文件上测试命令的正确性，确认编码不会被破坏。

**正确流程**：
1. 先用 `Get-Content -Encoding UTF8` 读取文件，确认内容正确显示
2. 在一个测试文件上执行替换命令
3. 打开替换后的文件，确认中文没有乱码
4. 确认无误后再批量操作

---

## 总结

| 错误 | 根因 | 修复 |
|------|------|------|
| `Set-Content` 损坏 UTF-8 | 默认 GBK 编码与 UTF-8 不匹配 | 加 `-Encoding UTF8` 参数 |
| 双重编码无法恢复 | 信息在编码转换中丢失 | 从备份恢复，无备份则手动修复 |
| 未测试就批量操作 | 缺少验证步骤 | 先在单个文件上测试命令 |

## 后续改进

### 改进 1：使用 Python 替代 PowerShell 做文本替换

对于复杂的文本替换操作，用 Python 更可靠，因为 Python 默认使用 UTF-8：

```python
# fix_imports.py
import re
with open('core/routes/routes_api.py', 'r', encoding='utf-8') as f:
    content = f.read()
content = content.replace('from core.workspace import', 'from core.path_policy.workspace import')
with open('core/routes/routes_api.py', 'w', encoding='utf-8') as f:
    f.write(content)
print('Done')
```

然后执行：
```powershell
python fix_imports.py
```

### 改进 2：配置 PowerShell 默认编码

在 PowerShell 配置文件中设置默认编码为 UTF-8：

```powershell
# 打开配置文件
notepad $PROFILE

# 添加以下内容
$PSDefaultParameterValues['*:Encoding'] = 'UTF8'
```

### 改进 3：操作前先备份

所有文件操作前先创建备份，防止损坏后无法恢复：

```powershell
Copy-Item "core/routes/routes_api.py" "core/routes/routes_api.py.bak"
```

## 本次新增的关键教训

### 教训 A：编码问题比想象中更隐蔽

**现象**：第一次执行替换后，代码能运行（因为损坏的是注释中的中文），但第二次替换时问题爆发。

**根因**：第一次损坏的是注释中的中文，不影响运行；第二次损坏了函数体中的中文错误消息，导致 Python 解析失败。

**教训**：编码损坏可能潜伏在注释中，看起来代码能跑，但随时可能因为后续修改而爆发。必须在每次操作后检查文件内容。

### 教训 B：Git 也无法拯救编码损坏

**现象**：尝试用 `git checkout` 恢复文件，失败。

**根因**：`git status` 显示文件已被修改但未暂存，说明损坏已经写入磁盘。如果没有之前的 commit 或 stash，Git 无法恢复原始内容。

**教训**：操作前先 `git stash` 或 `git commit`，确保有可回滚的版本。

## 最终结论

本次编码损坏事件的根本原因是 PowerShell `Set-Content` 默认编码与项目 UTF-8 编码不匹配。后续所有文件操作必须遵循以下原则：

1. PowerShell 操作文本文件时，始终加 `-Encoding UTF8`
2. 批量替换操作优先使用 Python 脚本
3. 操作前先备份，操作后检查文件内容
